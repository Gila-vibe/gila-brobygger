# Harness Engineering

The harness is the project's safety net: a small, dependency-free set of scripts and conventions
that make every change **checkable, reviewable and reversible**. It is deliberately boring –
standard-library Python, plain files, no services to maintain.

## 1. Goals

1. Catch broken links, missing assets and malformed pages before they reach the domain.
2. Enforce the organisation's content and privacy rules mechanically where possible.
3. Make approvals and open questions visible instead of implicit.
4. Keep the site buildable and deployable by a non-developer.
5. Give CI a single, fast, deterministic gate.

## 2. Layout

```
harness/
├── config/
│   └── site.json          # pages, navigation, contact details, policy flags
├── scripts/
│   ├── check_site.py      # HTML, links, assets, metadata, accessibility basics, policy
│   ├── check_secrets.py   # secret and credential scan
│   └── check_docs.py      # documentation presence and consistency
└── reports/
    ├── README.md          # what reports are and how they are produced
    └── latest.json        # generated by check_site.py (git-ignored or refreshed)
```

## 3. Gates

| Gate | Script | Blocks when |
|---|---|---|
| Site integrity | `check_site.py` | missing page, broken link/anchor/asset, bad metadata, missing skip link, external runtime resource, form, cookie/tracking marker, EXIF in published JPEG |
| Secret exposure | `check_secrets.py` | private key, token, password, `.env`, suspicious credential file |
| Documentation consistency | `check_docs.py` | required doc missing, broken internal link, contact/page facts out of sync |

All three run in `.github/workflows/quality.yml` on push and pull request. They also run locally
before a change is reported as complete.

## 4. Configuration

`harness/config/site.json` is the single source of truth for structural expectations:

```json
{
  "domain": "gila-brobygger.dk",
  "base_url": "https://gila-brobygger.dk",
  "publish_dir": "docs",
  "entry_point": "index.html",
  "required_pages": ["index.html", "..."],
  "noindex_pages": ["404.html"],
  "navigation": [{"href": "index.html", "label": "Forside"}, "..."],
  "footer_links": ["kontakt.html", "privatliv.html", "..."],
  "contact": {"email": "...", "phone_display": "...", "phone_href": "..."},
  "assets": {"stylesheet": "assets/css/styles.css", "script": "...", "favicon": "..."},
  "policy": {
    "allow_forms": false,
    "allow_external_resources": false,
    "allow_analytics": false,
    "require_skip_link": true,
    "require_meta_description": true,
    "require_canonical": true
  }
}
```

Changing the config is a structural change. Update the website, the sitemap and the documentation
in the same change.

## 5. What is checked, and why

| Area | Rationale |
|---|---|
| Entry point and CNAME | A wrong path or CNAME silently breaks GitHub Pages |
| Internal links and anchors | Most common real-world regression |
| Local assets | Prevents broken images, CSS and JS |
| Titles, descriptions, canonical | SEO and sharing quality |
| One `h1`, landmarks, skip link, alt text | Accessibility basics that are cheap to verify |
| Duplicate IDs | Breaks anchors and assistive technology |
| External runtime resources | Privacy: no third-party requests without review |
| Forms and tracker markers | No data collection without approval |
| EXIF in JPEGs | Prevents publishing GPS/location metadata |
| Placeholder markers | Prevents shipping TODO text |
| Secrets | Prevents credential leakage |
| Documentation set | Prevents the "documented but missing" drift |

## 6. Report format

`check_site.py --report <path>` writes JSON:

```json
{
  "generated_at": "2026-11-08T00:00:00Z",
  "root": "docs",
  "pages_checked": 14,
  "errors": [],
  "warnings": [],
  "passed": true
}
```

CI uploads the report as an artifact. A local run should be summarised in the change report.

## 7. Adding a page

1. Create `docs/<page>.html` from the shared shell (header, main, footer, script).
2. Add it to `harness/config/site.json` (`required_pages`, or `noindex_pages` for error/utility
   pages that must not be indexed).
3. Add it to navigation/footer if it belongs there.
4. Add it to `docs/sitemap.xml` unless it is `noindex`.
5. Update `docs/WEBSITE_SPEC.md` and `README.md` if the inventory changed.
6. Run all checks.

## 8. Adding a check

- Add it to the most relevant script; keep one responsibility per script.
- Emit a clear error message with file and line where practical.
- Prefer false negatives over noisy false positives, but never delete a meaningful check.
- Add a test case or a fixture page if the check is non-trivial.
- Update this document and `docs/TESTING.md`.

## 9. Changing a rule

If a rule blocks a legitimate change:

1. Confirm the rule is not protecting privacy, accessibility or a legal obligation.
2. Write a short decision record in `docs/decisions/`.
3. Get owner approval; legal/DPO review if data is involved.
4. Update config, script, tests and documentation together.
5. Record the exception and its expiry in `docs/APPROVAL_LOG.md`.

Never bypass a gate by editing the workflow to skip a script.

## 10. Continuous improvement

- After each release, add one check for the most likely next regression.
- Keep the harness fast (target: under a few seconds on a laptop).
- Remove checks only when the underlying risk is gone, not when they are inconvenient.
- Review `docs/OWNER_REVIEW.md` and `docs/QUALITY_SCORE.md` at each planning cycle.
- Treat every incident as a missing check or a missing approval gate.

## 11. Limitations

- No browser rendering in CI; visual and interactive behaviour are checked manually.
- No full HTML validator; the parser used is intentionally tolerant.
- No link checking against the live domain; deployment verification is separate and owner-approved.
- No guarantee that content is true; the harness checks structure and policy, humans check facts.
